## 🔴 Critical(必修)

### C1. `htmlEscape` 输出未转义 `%`,污染 `string.gsub` 替换串

- 位置:`waf.lua:126-129, 131`
- 触发:`string.gsub(content, "{BLOCK_REASON}", htmlEscape(msg))` 中第三参数是字符串,`%` 是元字符(`%0`/`%1`-`%9` 表示捕获引用)。debug 模式下 `msg` 含攻击者输入(如 URI 含 `%20`),`htmlEscape` 不转义 `%`,`gsub` 抛 `invalid use of '%' in replacement string`,导致 `ret403` 异常退出。
- 后果:debug 模式下 WAF 拦截链在响应阶段崩溃;非 debug 模式下 `msg` 由代码常量提供,暂未触发,但属时间炸弹。
- 修复:用 function 替换形式(最稳)
  ```lua
  content = string.gsub(content, "{BLOCK_REASON}", function() return htmlEscape(msg) end)
  ```
  或在 `htmlEscape` 内再过一遍 `gsub("%%", "%%%%")`。

### C2. `cjson.encode` 对非法 UTF-8 抛 error,攻击日志会丢失整条

- 位置:`waf.lua:151`
- 触发:`self.headers` 包含攻击者注入的非法 UTF-8 字节(很常见),`cjson.encode` 直接 `error()`(不返回 nil+err),`Waf:inAttack` 整个被中断,攻击不仅未拦截、连日志也没写。
- 修复:用 `cjson.safe`:
  ```lua
  local cjson = require "cjson.safe"   -- 顶部 require 改这里
  ```
  或 `local ok, logStr = pcall(cjson.encode, logTable); if not ok then ... end`。

### C3. `cacheIncr` 把"滑动窗口"悄悄改成"固定窗口"

- 位置:`utils/cache.lua:29`、`waf.lua:190, 197, 224`
- 行为变化:`dict:incr(key, inc, 0, ttl)` 的 `ttl` **仅在 key 不存在时生效**;key 已存在时 incr 不刷新 TTL。
  - 旧实现 `cacheSet(key, n+1, ttl)`:**滑窗**——每次写都重置 TTL
  - 新实现 `cacheIncr`:**固定窗**——首次创建定 TTL
- 后果:
  - **CC 防护**:从"最近 60s 内 >100 次" 退化为"自首次起 60s 固定窗口",存在边界 burst(窗口末 + 下窗首 加倍)。
  - **possibly 计数**:攻击者可摸准窗口边界做规避。
- 修复(任选一种,必须在 commit 里明确语义):
  - 接受固定窗口 → 把 `cc_seconds` 在配置和 MEMORY 中改名为 `cc_window_seconds`,更新文档。
  - 保留滑窗 → incr 后判断"是首次"(返回值 == inc)就显式 `cache:expire(key, ttl)`:
    ```lua
    local v = self.cache:incr(key, inc, 0, ttl)
    if v == inc then self.cache:expire(key, ttl) end   -- 每次刷 TTL
    ```

### C4. `rules/path.lua:51` 注入的 `%c0%af`/`%c1%9c` 规则**必然失效**

- 位置:`rules/path.lua:51`
- 现象:pattern 含 `\.\.%c0%af`、`\.\.%c1%9c`。**但 MEMORY 已明确教训**:引擎 `UnEscapeUri` 递归 `ngx.unescape_uri`,`%c0` `%af` 等标准百分号编码在到达规则匹配前**已被解码为字节** `\xc0\xaf`,规则永远匹配不到字面 `%c0%af`。
- 后果:这两条 confidence=3 规则形同虚设。`%u2215`/`%u2216` 是非标准 IIS Unicode 编码,ngx.unescape_uri 不处理,**这部分有效**。
- 修复:拆开
  ```lua
  -- 保留(有效)
  pattern = [[ (?:\.\.;/|\.\.%u2215|\.\.%u2216) ]],
  -- 改为匹配解码后字节(如要保留 c0/af 检测)
  pattern = [[ \.\.\xc0\xaf|\.\.\xc1\x9c ]],
  ```

### C5. `Waf:UnEscapeUri` 末尾 `string.lower` 之后的隐式约束

- 位置:`waf.lua:301`
- 触发:所有 checkData 元素(含 body)都被 lower 化。pattern 在 init 阶段**没有** lower(init.lua:128 只做 trim),加上 `"isjo"` 中 `i` 已经做大小写不敏感匹配,data 的 lower 是冗余 CPU。
- 但更要紧的是:对大 body(如 multipart 上传 10MB)每个请求做一次 `string.lower` 是热路径的常量复制,性能浪费可见。
- 修复:删除 line 301 的 `string.lower(...)`,直接 `return decoded_uri_2`。`"isjo"` 已覆盖大小写匹配需求。
- 注意:删除后要回归测试现有规则是否仍然命中(理论上 i flag 等价)。

## 🟠 High

### H1. 规则匹配嵌套顺序导致 position 前缀重复检查

- 位置:`waf.lua:354-373`
- 当前顺序:`data → rule → patternItem → position`
- 问题:同一 rule 的所有 patternItem 共享相同 `positions`,但循环把 position 检查放在最内层,每条 pattern 都重做一次前缀匹配。`rules/sqli.lua` 有 ~30 条规则、3 个 position,单条 data 多做 ~90 次 `sub+eq`。
- 修复:position 检查上提到 rule 层
  ```lua
  for _, data in ipairs(checkData) do
      for _, rule in pairs(RULE_FILES) do
          local hit_pos = nil
          for _, p in ipairs(rule.positions) do
              if data:sub(1, #p) == p then hit_pos = p; break end
          end
          if hit_pos then
              for _, patternItem in pairs(rule.rules) do
                  if ngx.re.match(data, patternItem.pattern, "isjo") then
                      self:inAttack(rule.name .. " - " .. hit_pos .. " - " .. patternItem.name, ...)
                      ...
                  end
              end
          end
      end
  end
  ```

### H2. 模块级 `WHITE_IP_SET` 等"加载时缓存"在 `access_by_lua_file` 下失效

- 位置:`waf.lua:34-36`
- 关键事实:`access_by_lua_file` 每次请求执行整个 chunk,**local 变量每个请求都重建**。新写法相比旧的"每次 Waf:new 调 listToSet"性能等价,没有改善。
- 修复:把构建移到 `init.lua` 的 `load_ips()`/`load_hosts()` 末尾,作为全局:
  ```lua
  -- init.lua
  WHITE_IP_SET, WHITE_HOST_SET, BLACK_IP_SET = {}, {}, {}
  for _, v in ipairs(WHITE_IPS) do WHITE_IP_SET[v] = true end
  -- ...同理
  ```
  waf.lua 直接 `if WHITE_IP_SET[self.ip] then`,set 在 init 阶段构建一次(O(N)),所有请求 O(1) 查询,所有 worker 共享(init 阶段全局表通过 fork 复制)。

### H3. `asyncLog` 中每条日志都新建 logger,丢失 batching

- 位置:`waf.lua:60`、`utils/logger.lua:7`
- 现象:每次攻击都 `ngx.timer.at(0, ...)`,timer 回调里 `logger:new(h)` 创建新对象(含 20000-cell buffer)。logger 内部 batching 设计需要**调用方持有同一实例**才生效;每次 new 导致单条日志就 flush(或等 1s timeout),失去 batching 意义。
- 后果:高频攻击(万级 qps)会创建大量 pending timer + 大量短生命 logger 实例 + 大量 20000 cell table,超出 `lua_max_pending_timers` 后日志丢失。
- 修复:logger 模块顶层维护实例表
  ```lua
  -- utils/logger.lua 顶部
  local loggers_by_host = {}
  function _M:new(host)
      host = sanitizeHost(host)
      if loggers_by_host[host] then return loggers_by_host[host] end
      local t = { ... }   -- 原构造
      setmetatable(t, mt)
      loggers_by_host[host] = t
      return t
  end
  ```
  另:waf.lua 的 `asyncLog` 可以省掉,直接 `hostLogger:log(s..'\n')` —— logger 内部已有 timer 推迟磁盘 IO。

### H4. `ngx.req.get_headers()` 默认 100 限制造成 WAF 盲区

- 位置:`waf.lua:75`
- 问题:默认 `get_headers()` 返回前 100 个 header,剩余截断(OpenResty 仅日志 WARN,Lua 侧无感知)。攻击者发 200 个 header 时,后 100 个**既不参与规则匹配也不进入日志**。
- 修复:`ngx.req.get_headers(0)`(0 表示无上限)或显式 `(1000)`,并在文档里声明上限。

### H5. `attack()` 中同步读 body file 是阻塞 syscall + 双重 read_body

- 位置:`waf.lua:331-343`、`waf.lua:395`
- 问题 1:`io.open(body_file, "rb"):read("*all")` 是阻塞 syscall,access 热路径上对大 body(百 MB)会冻结 worker。
- 问题 2:`calculateRequestSize`(在 `isBigRequest` 内)和 `attack` 各 `read_body` 一次;第二次虽 no-op,但顺序上是 **"先 read_body 再判断是否超大"**——nginx 已经把 body 收完才判断上限,绕过了 isBigRequest 的本意。
- 修复方向:
  - 用 nginx 层 `client_max_body_size` 做硬上限,Lua 不再重复防御。
  - 若必须 Lua 层防:`tonumber(ngx.var.content_length)` 不存在或超限直接 ret403,**不进入 read_body**。
  - 共享一次 body 读取:把 body 缓存到 `self.body`,calculateRequestSize 和 attack 复用。

## 🟡 Medium

### M1. `rules/cmd.lua:62` PowerShell `iex` 规则漏报

- pattern:`\b(?:iex|invoke-expression|...)\b\s*[\(\s]`
- 问题:`\s*[\(\s]` 表示"零或多空白后跟 `(` 或空白"。命令 `iex foo`(一个空格)走法:`\s*` 吃掉空格,`[\(\s]` 需要 `(` 或空白,但下一个字符是 `f`——**不匹配**,漏报。
- 修复:`\b(?:iex|...)\b(?:\s+|\s*\()`

### M2. `rules/cmd.lua:67-71` 危险 cmdlet 不分词

- pattern:`new-object\s+(?:net\.webclient|...)` 与 `\.(?:downloadstring|downloadfile|downloaddata)\s*\(`
- 风险:业务字符串中如恰含 `obj.DownloadString(` 之类的字面,confidence=3 直接拦。WAF 严格设计可接受,但建议把第二条限定上下文(前面有 webclient 之类标识)。

### M3. 规则文件 schema 被引擎注入字段(架构)

- 位置:`init.lua:124, 129`
- `rule.positions` 与 `item.pattern` 被引擎写回 require 返回值。规则文件作者打开看不到 `positions` 字段,但引擎依赖;且 require 缓存共享,多 worker 引用同一表。
- 修复:把派生结构存到引擎自己的表里
  ```lua
  RULE_FILES[key] = {
      meta = rule,         -- 原始(不可变)
      positions = positions,
      rules = preprocessed_rules,
  }
  ```
  访问改成 `rule.meta.name / rule.meta.level / rule.meta.desc`。

### M4. position 取值与前缀匹配的隐式契约

- 位置:`waf.lua:359` vs `rules/*.lua` `position = "uri,body,cookie"`
- 问题:若有人写错 `"User-Agent"`(大写)或 `"boddy"`(错字),引擎照跑、规则静默失效、无任何告警。
- 修复:`init.lua:load_rules` 预处理 positions 时白名单校验:
  ```lua
  local VALID_POS = { uri=1, body=1, cookie=1, ["user-agent"]=1 }
  for _, p in ipairs(positions) do
      if not VALID_POS[p] then
          ngx.log(ngx.WARN, "rule ", key, ": unknown position '", p, "'")
      end
  end
  ```

### M5. `utils/logger.lua` sanitizeHost 不处理纯点 host

- 位置:`utils/logger.lua:14-24`
- 现象:去 `[\\/:*?"<>|\x00-\x1f]` 和首尾空白/尾点后,host = `..` 这种**全是点且非首尾**的串保留下来。
- 影响:Windows 上 `..log` 这种是合法文件名但会引发歧义。
- 修复:第二步正则加 `^[.\s]+|[\s.]+$`(去首尾点和空白);或 sanitize 后做 `if s:match("^%.+$") then return "unknown" end`。

### M6. `UnEscapeUri` 函数 SRP 膨胀

- 70 行同时承担"递归 URL 解码"、"递归 HTML 实体解码(含命名实体/十进制/十六进制/UTF-8 编码)"、"小写化"。
- 建议(非阻塞性):抽到 `utils/decoder.lua`,把 `NAMED_ENTITIES` 表移到 decoder 模块。便于单元测试与维护。
